# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A retro first-person shooter (Quake / early Half-Life look) in **Godot 4.7** with GDScript only (standard build, not .NET). No addons, no build step, no test suite, no linter. `README.md` is the user-facing manual (controls, every tunable setting, known limitations) — update it when adding weapons, enemies, scenes, shader settings or controls.

## Commands

The Godot executable is not on PATH. It lives at `C:\Users\jonat\Documents\Godot_v4.7-stable_win64.exe\Godot_v4.7-stable_win64_console.exe` (the folder is named like an `.exe`). ```

```
# Regenerate the placeholder textures after editing the generator
Godot_v4.7-stable_win64_console.exe --headless --path . --script res://scripts/tools/generate_textures.gd

# Rebuild the blocky zombie's meshes (assets/meshes/) and its looks (assets/textures/zombie_look_NN.png), then run --import if a PNG changed
Godot_v4.7-stable_win64_console.exe --headless --path . --script res://scripts/tools/generate_zombie.gd

# Rebuild the block palette (assets/blocks.tres) after editing scripts/blocks.gd
Godot_v4.7-stable_win64_console.exe --headless --path . --script res://scripts/tools/generate_blocks.gd

# Rebuild levels/test_room.tscn (overwrites editor changes to it)
Godot_v4.7-stable_win64_console.exe --headless --path . --script res://scripts/tools/build_test_room.gd

# Parse-check one script without running the game
Godot_v4.7-stable_win64_console.exe --headless --path . --check-only --script res://scripts/player.gd

# Re-import assets (needed after adding/changing files outside the editor)
Godot_v4.7-stable_win64_console.exe --headless --path . --import

# See what the editor's Debugger panel would list when the game starts
Godot_v4.7-stable_win64_console.exe --headless --path . -d --quit-after 240
```

That last one matters because GDScript warnings (a shadowed name, an unused variable...) are sent only to an attached debugger: they are never printed by a plain run and never reach `user://logs/godot.log`. `-d` attaches a debugger that prints them, each as `WARNING: ... at: GDScript::reload (res://scripts/x.gd:LINE)`, once per script the first time it is loaded. Add `--script` to run a test the same way, but give it a time limit: on a script error this debugger stops at a `debug>` prompt and waits.

## Architecture

### Rendering pipeline (`scenes/main.tscn` + `scripts/main.gd`)

`Main` (a `Control`) owns the low-res look and is the root of every running game, but it is no longer the project's main scene: `run/main_scene` is `levels/start-level-demo.tscn`, and `LevelLauncher` (see **Gameplay conventions**) swaps a game started on a level for `main.tscn` with that level in it. The entire game — the level **and** the HUD — lives inside `ViewportContainer/GameViewport`, a `SubViewport` sized by `render_size` (640x480 for now; the game was made at 320x240, which is kept as a commented-out line beside it). Only the 3D is drawn at that size. `hud.tscn`, `pause_menu.tscn` and `notebook_reader.tscn` are laid out in pixels of a 320x240 picture, and `main.gd`'s `_scale_interface()` keeps them that way at any `render_size` by setting the viewport's `size_2d_override` (with `size_2d_override_stretch`) to a canvas `INTERFACE_HEIGHT` (240) tall and as wide as the picture's shape makes it (320 for 4:3). So every 2D position and size inside `GameViewport` is in those units, not render pixels, and at 640x480 each one is drawn 2x2. Mouse positions arriving in `_unhandled_input` inside the viewport are converted to the same units by the engine, which is what `pause_menu.gd`'s `_row_at` compares with `get_global_rect()`. New UI should be laid out for 320x240 too. The notebook's page has fixed positions for a canvas 320 wide, so it is only centred at 4:3. `main.gd` scales the container to the window (4:3, letterboxed, nearest-neighbour) and the container carries `shaders/color_quantize.gdshader` as a post-process over the finished frame.

Consequences to keep in mind:

- Anything that must look chunky (new UI, effects) goes inside `GameViewport`, not under `Main` directly.
- Levels are not baked into `main.tscn`. `Main` has an exported `levels: Array[PackedScene]`; `main.gd` instantiates `levels[level_index]` as the first child of `GameViewport` and the `level_next`/`level_previous` actions (F2/F3) swap it, but only while `Main`'s exported `level_switching` is true. It is false for now (the user asked for level switching to be disabled "for now"; the actions are still in `project.godot` and the other levels still in the array, played with F6). The `level_restart` action (F5) is not behind that switch: `main.gd`'s `restart_level()` calls `reload_current_scene` offline (exactly what the player's death does), `load_level()` when hosting (a fresh level and fresh players for everyone, as for a change of level) and nothing on a client. It is read in `Main`'s `_unhandled_input`, and `Main` is pausable, so it does nothing while the pause menu or a notebook's page has the game paused: that is on purpose, because `get_tree().paused` would survive the reload and leave a frozen game with no menu showing. `level_index` is `static` so it survives the `reload_current_scene` on player death. A new level must be added to that array in `main.tscn`. The levels the user named use hyphens (`half-life-level.tscn`, `test-map.tscn`, `test-map-2.tscn`, `start-level-demo.tscn`, `multiplayer-map-demo.tscn`); `test_facility.tscn` and `test_room.tscn` are snake_case. `start-level-demo.tscn` is first in the array and is the project's main scene too, so it is the level the game starts in either way; `multiplayer-map-demo.tscn` (the arena with rounds of zombies, see **Rounds** below) is second; `test_room.tscn` (the block-built destruction test, see **Destruction** below) is last.
- Compatibility lights at most 8 omni/spot lights per mesh, and a CSG level's combiner is one mesh. Keep a CSG level to about 6 `OmniLight3D`s (the muzzle flash is another) and lean on ambient light. A GridMap (the block-built levels) is drawn in octants (8x8x8 cells), each its own mesh, so lights only compete within an octant; still keep lights few there too.
- Mouse look uses `event.screen_relative`, not `relative`, because the viewport is scaled.
- **Pausing**: `scenes/pause_menu.tscn` (inside `GameViewport`, `PROCESS_MODE_ALWAYS`) owns Esc and F1 and sets `get_tree().paused`. `ViewportContainer` is also `PROCESS_MODE_ALWAYS` so it keeps forwarding input into the SubViewport while paused; that is inherited by everything inside it, so `main.gd` sets each loaded level to `PROCESS_MODE_PAUSABLE` and the HUD instance is pausable too. Anything new added directly under `GameViewport` must be made pausable the same way. Paused nodes miss input (e.g. a button release), so per-input state like the machine gun's `trigger_held` is reset on `NOTIFICATION_PAUSED`. The Graphics page's FULLSCREEN row sets the window mode with `DisplayServer` and reads it back from the window rather than storing it. The Audio page's MASTER VOLUME keeps a static `master_volume` (0 to 1, steps of 0.1) and applies it to audio bus 0 in `_apply_settings` (muting the bus at 0).
- The renderer is **Compatibility (GL)**. Forward+/Mobile-only features (`Decal`, etc.) are unavailable — bullet holes are textured quads for this reason. No AA, tonemapping, glow or mipmaps; texture import defaults in `project.godot` disable compression and mipmaps.

### Surfaces

Every 3D surface uses a material in `assets/materials/` built on `shaders/retro_surface.gdshader` (vertex snapping, banded lighting, optional affine warping). Its `viewmodel` uniform fakes the depth so the first-person gun draws over walls; `player.gd` turns it on in material copies for every mesh under `Head/Camera3D` (don't make it an `instance uniform`: every retro-shaded mesh then takes an instance slot and the big levels run out). The shader **generates its own UVs** by box-mapping from world position (`uv_from_world = true`, for level geometry) or object position (for props), so mesh UVs are ignored. Shader uniform defaults are global; materials override per-surface.

On top of the per-material uniforms, the effects are scaled by **shader globals** (`global uniform`, declared in `project.godot` under `[shader_globals]`): `retro_effects` (master switch, also read by `color_quantize.gdshader`), `retro_snap_strength`, `retro_light_band_strength` and `retro_color_quantize`. `pause_menu.gd` keeps the current values in static vars (initialised from `ProjectSettings` in `_static_init`) and pushes them with `RenderingServer.global_shader_parameter_set`; `global_shader_parameter_get` does not work at runtime. A new shader that declares a global needs that global to exist in `project.godot`, or it fails to compile. The editor only reads `project.godot` at startup, so after editing that section on disk the editor needs Project > Reload Current Project (and saving Project Settings from a stale editor would drop the section).

Textures in `assets/textures/` are generated by `scripts/tools/generate_textures.gd` (an `extends SceneTree` tool script with a fixed seed, not part of the game) and committed as PNGs. Every texture draws from one shared `rng`, so new textures go at the end of `_init` (otherwise every texture after the insertion changes). For the same reason, redrawing an existing texture must not change how many random numbers it uses (`_make_poster_chart` keeps its `_new_poster(64, 48, ...)` and draws the rest without `rng`; `_make_whiteboard` gets its board from `_new_whiteboard()`, which takes exactly the numbers that function used to take itself, and both whiteboards write and frame theirs without `rng`; `_make_glass_crack` throws away the `GLASS_CRACK_OLD_DRAWS` (612) numbers its first version took and draws with a `RandomNumberGenerator` of its own, so its `dice.seed` or its drawing can change freely; `_make_glass_edge` does the same with `GLASS_EDGE_OLD_DRAWS` (88)); after a run, `git status` should show only the PNGs you meant to change. Text on posters and signs is drawn with `_draw_text`/`_draw_text_centred`, which use `pixel_text.gd`'s `GLYPHS`. The one set of textures this tool does not make is the blocky zombie's looks (`zombie_look_NN.png`): those come from `scripts/tools/generate_zombie.gd`, which never touches the shared `rng` (see **Blocky zombie** below).

### Gameplay conventions

There are no signal buses or base classes. There are two autoloads: `LevelLauncher` (`scripts/level_launcher.gd`): when the game is started on a scene under `levels/` (the project's main scene is one, and F6 runs any other), it sets `direct_level_path`/`open_direct_level` (statics in `main.gd`) and changes scene to `main.tscn`, so the level gets the viewport, HUD and pause menu; and `Network` (`scripts/network.gd`, see Multiplayer below). Scripts are wired together by a few duck-typed conventions:

- **Damage**: anything with a `take_damage(amount: int)` method can be hurt. Weapons call it on whatever a ray hits; if the collider lacks it, they spawn a bullet hole instead. Enemies call `player.take_damage()`. Every `take_damage` is `@rpc("any_peer", "call_remote", "reliable")` and starts by forwarding itself with `rpc_id(get_multiplayer_authority(), ...)` when called on a non-authority copy; keep that for anything new that can be hurt.
- **Blood**: things that bleed implement `bleed(at, spray_direction, drop_count := 12)`; weapons and explosions call it (if present) just before `take_damage`. `bleed` broadcasts with `_bleed.rpc(...)` (`call_local`) so every peer shows it; the authority's copy also records `wounded_limb`, which works because reliable RPCs from one peer arrive in order. Enemies spawn `blood_splash.tscn` tinted by their exported `blood_color`.
- **Surface marks**: bullet holes, grenade scorch marks and blood stains are alpha-scissored quads sharing `surface_mark.gd` (`bullet_hole.tscn`, `blood_stain.tscn`), capped per `kind`. `structure.gd` frees marks whose block is destroyed (it looks just behind each mark's +Z face). `place(position, normal, size)` returns false and frees the mark if any corner would hang in the air (per-corner raycasts), so callers must not use the node after a failed `place`. `blood_splash.gd` leaves the stains by raycasting from the wound, skipping anything with `take_damage`.
- **Dismemberment** (`enemy.gd`, enabled per scene by `loses_limbs`; on for the zombie): `bleed()` records which limb the wound is on from the hit's height and side in the enemy's local space (`"random"` for a `Vector3.ZERO` blast), and the following `take_damage()` adds the damage to that limb. So weapons must keep calling `bleed` immediately before `take_damage`. When a limb reaches `limb_health` it rolls once against `head_loss_chance`/`leg_loss_chance`/`arm_loss_chance`; a limb that survives the roll goes in `sturdy_limbs` and can never be severed. A severed limb node is reparented into a `gib.tscn` in the level, and the script's limb variable is repointed at an empty stand-in `Node3D` so animation and death tweens keep working.
- **View bob**: `player.gd`'s `_bob_view()` (from `_process`) offsets `Head/Camera3D`'s local position by distance walked; the weapons are camera children so they move with it, and it also swings `current_weapon` around its entry in `weapon_rest_positions` (the weapon node; recoil tweens move each weapon's `Model` child, so don't animate the weapon node's position elsewhere). It is switched by the static `view_bob` in `pause_menu.gd` (the VIEW BOB row on the Graphics page), which `player.gd` reads through a `preload` of that script.
- **Hurt feedback**: `player.take_damage` sets `hurt_flash` to 1 (it decays in `_process`) and plays `HurtSound`; the HUD polls `hurt_flash` to set the alpha of its full-screen `DamageTint`.
- **Particles** (blood, explosion smoke) are one-shot `CPUParticles3D` with unshaded, particle-billboarded square quads, configured in the `.tscn` rather than in code.
- **Crates** are `crate.tscn` instances (a `CharacterBody3D` in the `"breakable"` group with `take_damage`, origin at the base, falls when unsupported), not CSG boxes. Because they have `take_damage`, shots leave no marks on them and explosions and blood-stain rays treat them like bodies.
- **Explosive pylons** (`explosive_pylon.tscn`) follow the crate pattern (`CharacterBody3D`, `"breakable"` group, origin at the base, falls when unsupported) and are placed under each level's `Props`. Their `bleed()` sprays sparks instead of blood. At 0 health they light a fuse, then spawn `explosion.tscn` with overridden `max_damage`/`radius` and a node `scale` for a bigger fireball. Chain reactions are just the blast damaging a neighbour (≥15 damage reaches about 4.25 m), and the fuse delay keeps them from recursing. Their timers use `create_timer(t, false)` so they stop while the game is paused; keep that for any gameplay timer.
- **Hazards**: `damage_zone.gd` on an `Area3D` calls `take_damage` on overlapping bodies every `interval` seconds; the visible lava/slime is a separate unshaded triplanar slab under the level's `Details` node, and the pit is a CSG subtraction placed after the floor slabs.
- **Finding the player**: every player (local and remote) is in the `"player"` group; enemies chase the closest one (`_closest_player`). The HUD uses the `"local_player"` group, which only the player this computer controls joins.
- **Player model** (`player_model_soldier.tscn`, a special forces soldier, instanced as `Model` in `player.tscn`) is the body other players will see. `player_model.tscn` (armoured hazard suit) is the earlier model, kept but unused; both run `player_model.gd`, which only relies on the shared node layout (`Hips/Legs/Leg*/Knee/Ankle`, `Hips/Upper/Head/Visor`, `Hips/Upper/PackLamp`, `Hips/Upper/Aim/Arm*/Elbow`, `Aim/ShotSound`, `Aim/Guns`), so gun models must be added to both. `Network` sets each player's `armor_color`, which recolours every mesh using the scene's exported `tinted_material` (`soldier_marker.tres`: armbands and pack panel; `player_armor.tres` on the old model). The soldier's limbs use tiling `soldier_camo`/`soldier_webbing` (the latter pale, tinted by `soldier_webbing/black/marker.tres`), and its head, helmet, vest and backpack are `uv_from_mesh` atlases like the zombie's. It has no collision and only reads the player (`_read_player()`: velocity, `is_on_floor()`, `crouch_amount`, `head.rotation.x`, `current_weapon.name`), so those are the values multiplayer will need to sync. It reads `player.grounded` rather than `is_on_floor()` (remote copies never call `move_and_slide`). It is hidden in first person; F4 (`change_view` action) cycles `player.view` through `FIRST_PERSON`, `BEHIND` (`Head/ChaseArm/ChaseCamera`) and `FRONT` (`Head/FrontArm/FrontCamera`, arm turned 180°). Everything under `Head/Camera3D` is the viewmodel, on render layer 2, which both third-person cameras' cull masks leave out. `show_shot(sound)` flashes the held gun model's `Flash` and plays the sound from its `AudioStreamPlayer3D` (`GameViewport` has `audio_listener_enable_3d` on for this). Legs are placed by solving the knee from the hip height (feet stay planted), and arms by a two-bone solve onto each gun model's `GripRight`/`GripLeft` markers.
- **Multiplayer** (`scripts/network.gd` autoload, ENet on port 7777, host = peer 1, `-- --host` / `-- --join=IP` on the command line or the pause menu's Multiplayer page). Offline the default `OfflineMultiplayerPeer` makes every node its own authority and `rpc()` with `call_local` just runs locally, so all network code must also be the single-player code path. Rules:
  - Levels online come from `Network.level_spawner` (spawn function `_make_level(index)`, which removes the baked `Player` and keeps its transform as `spawn_point` and its `starting_weapon` as `spawn_weapon`, which `_make_player` gives every spawned player); `main.gd` has `load_level()` / `clear_level()` / `adopt_level()`, and clients never load levels themselves. Players come from `Network.player_spawner` (spawn path = the current level), named after their peer ID; `player._enter_tree` sets the authority from the name. Remote players: model visible, `Head/Camera3D` hidden and `PROCESS_MODE_DISABLED` (so their weapons ignore our input), no physics or input. `player.tscn`'s camera must not have `current = true` (a spawned remote player would steal the view); the local player calls `make_current()`.
  - Synced state lives in `Sync` (`MultiplayerSynchronizer`) nodes: player (position, rotation, velocity, `Head:rotation` every frame; `grounded`, `crouching`, `crouch_amount`, `weapon_index` on change) and the zombies (position, rotation, velocity at 20 Hz with velocity dead reckoning on clients; `death_direction`, `state`, `attacks`, `severed` on change, in that order). Enemy visuals are driven by setters on those vars (`state` → alert/death, `attacks` → attack anim, `severed` → `_lose_limb`), so on-change sync also brings late joiners up to date. Only the authority runs enemy AI/physics.
  - Shots: weapons aim from `owner.camera` (never `get_viewport().get_camera_3d()`), then call `owner.share_shot(self, data)`; the player RPCs `_replay_shot` and remote copies call the weapon's `replay_shot(data) -> AudioStream`, which repeats it with `hurts`/`deals_damage = false` (bullets, grenades, rockets and `explosion.tscn` all have `deals_damage`). The shooter's copy does hit detection and damage.
  - Crates and pylons: authority breaks/lights via `.rpc()` and calls `Network.record_destroyed(self)` so late joiners free them. `damage_zone.gd` only bites on the server. Player death online respawns (`_respawn`, `Network.find_spawn_position`) instead of reloading. The pause menu doesn't pause online; the player ignores input while the mouse isn't captured (`_has_control`).
  - UPnP: `host()` opens the port with Godot's `UPNP` class on `router_thread` (discovery blocks for ~2 s). The thread only writes `router_answer` and calls `_router_answered.call_deferred()`; the main thread joins it in `_finish_asking()`. `_close_router_port()` (leave, host lost, `_exit_tree`) deletes the mapping. `use_upnp = false` (or `-- --no-upnp`) skips it: set it in any test that hosts, or the test opens a real port on the user's router.
  - Testing (a `--script` run does not load the main scene, and `LevelLauncher` only looks once, at start: to go through the real start-up, `change_scene_to_file` the main scene and then call `root.get_node("LevelLauncher")._wrap_level()`; a headless window is 64 x 64 with the picture at y 8 to 56, so a made-up mouse event needs a `position` inside that, such as (32, 32), or it never reaches the game; a made-up key press (`Input.parse_input_event` of an `InputEventKey` with `physical_keycode` and `pressed` set) needs no position and reaches `Main`'s `_unhandled_input` as it is, which is how F5 was tested; a headless run cannot capture the mouse either (`Input.mouse_mode` stays visible), so `_has_control()` is false and the player ignores the keys: to walk it about with `Input.action_press`, instantiate the level yourself, `set_script` its `Player` to a `GDScript` that `extends "res://scripts/player.gd"` and returns true from `_has_control()`, set `starting_weapon` again, and hand the level to `main.adopt_level()` after `main.clear_level()`; and press actions after `await process_frame`, because one pressed in the middle of a physics step is `is_action_pressed` in that step but `is_action_just_pressed` only in the next): run several `--headless --script` processes with `-- --role=...` and a shared timeline; use `change_scene_to_file` for main (with `root.add_child` there is no current scene, so `reload_current_scene` on leave/death errors). A SceneTree script has no `multiplayer`; use a node's. `Engine.time_scale` alone makes every physics step longer rather than running more of them: to hurry a test, raise `Engine.physics_ticks_per_second` (and `max_physics_steps_per_frame`) by the same factor. When the host changes level with a client connected, the host usually logs `Node not found: ".../<client id>/Sync"` and `Failed to get cached node`: the client's player was still sending as its level went. It happens between any two levels and is harmless.
- **Crouch** (`crouch` action, Ctrl/C) swaps `CollisionShape3D` between the scene's capsule and a shorter duplicate made in `_ready`. Never resize the scene's shape: it is a sub-resource shared by every player instance. Standing up is checked with `test_move`. In mid-air, crouching moves the body up by the height difference instead of lowering the view (crouch-jump).
- **Ladders** (`ladder.tscn`/`ladder.gd`, `@tool`; only `start-level-demo.tscn` has one) are a port of Half-Life's `PM_LadderMove`, because the user asked for a ladder that works "like half-life's": keep that behaviour, quirks included, unless asked otherwise. A ladder is a prop (a `Node3D` in the `"ladder"` group, origin at the middle of its foot against the wall, climbed from its +Z side) with no `Area3D` and no collision. Its `holds(feet, radius, body_height)` is a `to_local` box test, like the zombie window's yard: the body's box against the climb volume (x within `width`/2, z from the wall out to `grab_distance`, y from 0 to `height` less 2 cm). `player.gd`'s `_physics_process` calls `_find_ladder()` (every node in the group) each step and, if one holds, `_climb()` instead of the floor or air branch: velocity is set outright (no gravity, no friction), wish = camera forward x forward key + camera right x sideways key, each times `ladder_speed` and deliberately not normalised; the part of it along the ladder's facing is taken out and turned into vertical speed (into the ladder = up), `is_on_floor()` and moving away adds a push off the foot, no keys = hang, and jump (held, as in Half-Life) sets velocity to facing x `ladder_jump_speed` and starts `ladder_wait` (`ladder_let_go_time`, 0.25 s with no ladder: the one thing Half-Life does not have, because at 60 steps a second a short tap would not clear a 20 cm volume). Nothing special happens at the top: the volume ends at `height`, the climb speed carries the player about 0.5 m up, and air control (1 m/s) takes them over the edge, which a capsule needs to be within about 0.28 m of to stand. That is why the ladder's wall must be flush with the edge of the floor above, and `height` exactly that floor's height. `grounded` stays `is_on_floor()`, so the body model shows its air pose on a ladder; nothing about ladders is synced (only the authority moves a player) and enemies ignore them. The rails are 1 m boxes scaled to `height` (so `ladder.tres`, a tinted `metal.png`, is world-mapped like level geometry) and the rungs are copies of the hidden `Rung` made by `_update()`, not saved in the scene.- **Weapons** are children of `Head/Camera3D` in `player.tscn` and are listed in the `weapons` array in `player.gd`. The active weapon is the `visible` one — each weapon reads the `shoot` action itself and must ignore it while hidden or while the mouse isn't captured. A weapon must implement `get_hud_text() -> String` (the HUD shows `player.current_weapon.get_hud_text()` every frame; the pixel font only has A–Z, 0–9, space and a little punctuation, see **HUD** below). Adding one also needs a `weapon_N` input action in `project.godot`; `player.gd` maps `weapon_N` to list position N-1 and the `weapon_next`/`weapon_previous` (mouse wheel) actions cycle the list. Projectile weapons start at `owner.get_projectile_start(muzzle_position)` (the barrel reaches past the capsule, through walls you stand against) and aim with `owner.get_aim_direction(start)`. For the player model to hold a weapon, add a gun model with the weapon node's exact name under `Hips/Upper/Aim/Guns` in `player_model_soldier.tscn` (and `player_model.tscn`), with `GripRight`/`GripLeft` `Marker3D`s.
- **Weapons use `owner`** (the player, as scene root) to exclude the shooter from raycasts, and `owner.get_parent()` (the level) as the parent for spawned bullets and bullet holes so they don't move with the camera.

  - Meshes are lofts: tables of `_ring(row, at, half_width, half_depth, shift, cut)` joined by `_add_loft()`, with a ring of no size closing each end (given the same `at` as the ring before it, it makes that end flat). A ring is a rectangle with `cut` taken off each corner along both sides, so `_ring_outline()` gives it eleven corners: the middle of the side it starts on, the two ends of each cut corner on the way round, the middle of the opposite side, and the first again at the other edge of the picture. A ring whose `cut` is its whole half depth has six sides (the hand). Which columns of a part's piece lie on which side is fixed for the whole part by a `..._SHARE` constant (`TORSO_SHARE = (10, 12)`: the front's flat is 10 columns either side of the middle column, the cut corner beside it ends at 12, and the side's flat gets the rest up to the next corner; the table at the top of the tool lists them all). They are chosen to suit what is painted (a breast pocket on the front of the chest, an ear in the middle of the side of the head) and not to match the sizes, so the sides of the head and torso have wider texels than their fronts. A "standing" part (head, torso, leg) is ringed round Y starting at the back (+Z) and going by +X, so in its piece of the picture the two edges are the middle of the back, the middle column is the front and the zombie's right is on the left: the picture is as seen from outside, and text reads the right way round. A "reaching" part (arm, foot) is ringed round Z starting underneath and going by +X, with the shoulder or heel in the top row. Triangles are `(a, b, c)` and `(b, d, c)` (Godot draws the clockwise side; `_save_mesh` reports a part that comes out inside out). Shading is flat: `_add_face()` gives every four-cornered face four corners of its own and one normal (the sum of its two triangles'), so nothing is shared between faces and every edge is hard. Each arm and each leg begins with a block centred on its pivot, as far behind the joint as above and below it, which is what hides the joint at any angle: keep that when reshaping, and keep the torso wide enough to bury it (the bottom of the torso is a box round the tops of the legs). The neck does the opposite and narrows towards its lower end: with the head turned and tilted at once (`rotation.y` 0.7 and `.z` 0.35 on top of the scene's 0.3 about X), the bottom corner of a neck as wide as its top came out through the slope of the shoulder.

### Destruction (block-built levels)

Destructible levels (only `test_room.tscn` so far) are built from 0.5 m blocks on two GridMaps sharing `assets/blocks.tres` (a MeshLibrary): `Shell` (plain, indestructible: foundation, outer skin of outer walls, optional lid) and `Structure` (`structure.gd`, export `shell` points at the Shell). Outer walls are two cells thick (shell outside, structure inside) so blasts crater them without opening the level. The level root also has `WorldEnvironment`, `Player` (spawn point), `Props`, `Enemies`, `Lights`. The retro shader's world-space UVs make adjacent blocks seamless; GridMap multimesh instances get correct `MODEL_MATRIX`.

- **Block types** live in `scripts/blocks.gd` (`TYPES`: name, material path, health, span; `RUBBLE` index). Item N of `blocks.tres` is `TYPES[N]`, so only append; then rerun `scripts/tools/generate_blocks.gd`. Tool scripts that need `blocks.gd` must not preload `structure.gd` (it references the `Network` autoload, which doesn't exist when a `--script` tool's constants compile; same reason `build_test_room.gd` uses `load()` inside `_initialize()`).
- **`test_room.tscn` is generated** by `scripts/tools/build_test_room.gd` (rerunning overwrites editor edits). Instances are created with `instantiate(PackedScene.GEN_EDIT_STATE_INSTANCE)` so the saved level only stores overrides.
- **Blast** (host only; `blast()` is `@rpc any_peer` and forwards like `take_damage`): blocks within radius, nearest first; damage falls off linearly from the nearest point of each block and is multiplied by `SHIELDING` (0.35) per block still in the way (blocks destroyed earlier in the same blast don't shield). Damage accumulates in `damage_taken`.
- **Support** (host only): integer "hold" per block in `held`, a widest-path flood from the shell with a bucket queue: shell below = `STABILITY` (240), resting on a block passes its hold on unchanged, hanging below costs `2*step`, sideways costs `step = STABILITY/span`. After removals `_rehold()` only invalidates blocks whose hold came through a removed block (exact-equality parent test) and re-floods them from their surviving neighbours; it matches a full `_hold_all()` (checked by a test). Blocks unheld at level start get a warning and are left alone.
- **Collapse**: newly unheld blocks are flood-filled into pieces; each drops rigidly (min free gap over its columns), `rubble_left` of its blocks survive and each tumbles to the lowest spot among its column and 4 neighbours (`_rubble_spot`), as `Blocks.RUBBLE`. The host computes everything and broadcasts `_apply(removed, falls)` (`call_local`); every peer animates the fall with a MultiMesh copy and places the rubble when the tween ends (`_land`; host also `_hold_new()` and `_crush()`). Clients only mirror `blocks`; a client's Structure `_ready` asks the host (`_send_changes`) for `changes` (cell -> type or -1) to catch up.
- Player and enemies can't step up 0.5 m yet; the test room's stairs have an invisible `StairRamp`.

## Code style

- Scripts are written for a reader learning Godot: a `##` doc comment header explaining the idea, `##` on every exported variable, and plain-language comments explaining *why* and what engine calls do. Match this density in new code.
- Gameplay tunables are `@export` variables (edited in the Inspector), not constants.
- Statically typed GDScript throughout (`:=`, typed parameters and return types).
- One script per scene, same base name (`scenes/foo.tscn` ↔ `scripts/foo.gd`).
- The project has no GDScript warnings; keep it that way. The ones that have crept in were all names: a parameter or local called after a built-in function (`wrap`, `sign`), or after a variable of its own script. A leftover use of such a name after renaming is not an error (it quietly means the built-in function), so search for it.

## Repo notes

- Commit `*.uid` and `*.import` files; `.godot/` is ignored cache.
- `.tscn`/`.tres` files are hand-editable text, but the editor rewrites them on save (e.g. reordering sections in `project.godot`), so expect incidental diffs.
- `ext_resource, invalid UID: uid://... - using text path instead` about a file whose own first line does carry that UID means this computer's `.godot/` cache is stale; the files are right and must not be edited to "fix" it. An editor that is running does not re-read the UID or the dependencies of a scene changed on disk (a `git pull`, a hand edit) unless that scene happens to be loaded, and the next time it starts it trusts its record for as long as the file's modified time matches (`.godot/editor/filesystem_cache10`: name, type, UID, time, ...). The game itself never reads the file: outside the editor `ResourceLoader.get_resource_uid` only looks in `.godot/uid_cache.bin`, which every editor start rebuilds from those records. The cure is to give the file a new modified time (`touch`, contents unchanged) and run `--import`, which re-reads it, and then to restart an editor that was open meanwhile (Project > Reload Current Project), because its memory still holds the old record and it writes that back the next time it saves the cache. This happened with `zombie_textured.tscn`, whose UID came in with a pull. It then came back within hours, because the user's editor stayed open (it often does for days, so do not count on a restart): the next time that editor re-imported anything it wrote its stale record over the corrected one. So `test_room.tscn`, the one file that named that UID, now refers to the scene by path alone, which cannot warn. A second trap of the same kind: `--import` rewrites `.godot/uid_cache.bin` whole, but an open editor only ever adds entries to the end of that file and then writes its own count of entries at the start. If its count is lower than what `--import` wrote, the file's last entries (the two shaders, which are scanned last) stop being read, and the game warns `invalid UID` for `color_quantize.gdshader` or `retro_surface.gdshader`. Running `--import` again puts the file right until that editor next adds an entry; only restarting the editor ends it. After any `--import` with the editor open, start the game with `-d` to see that no such warning has appeared, and tell the user to reload the project. Do not edit files under `.godot/` by hand.
